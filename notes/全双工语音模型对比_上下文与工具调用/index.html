全双工语音模型横向对比：上下文消耗与工具调用¶

整理日期：2026-10-27 关注问题：语音进、语音出、能实时用工具的全双工模型，会不会把上下文窗口撑爆？各家框架怎么应对？ 覆盖范围：Moshi 系（含 PersonaPlex、Hibiki、MoshiRAG、KAME 等）、SALMONN-omni 系（v1 / v2 / SALMONN-duo）、模块化双工（Freeze-Omni、MinMo、VITA）、时分交错单序列（SyncLLM、OmniFlatten、BayLing-Duplex、MiniCPM-o 4.5）、Thinker-Talker（Qwen2.5/3/3.5-Omni）、轮次式基线（GLM-4-Voice、Step-Audio 2、Kimi-Audio），以及商用 API（OpenAI GPT-Live / gpt-realtime、Gemini Live、Qwen-Omni-Realtime）。 可信度标注：数字已对照 arXiv HTML 原文或官方文档核对。[推算] 表示根据原文参数算出来的值，原文没有直接给出；[存疑] 表示原文没写清楚，或者只读到了摘要。

一、先说结论¶

  1. 上下文“爆炸”的根源是“每帧都占一个位置”加上“自己说过的话也回灌进上下文”，跟用不用 codec 关系不大。 去掉 codec 的 SALMONN-omni，每秒占用的位置数反而是 Moshi 的约 5 倍 [推算]。真正省上下文的是另一类设计：只把文本留在 LLM 历史里（Freeze-Omni、MinMo、MiniCPM-o 4.5、Qwen-Omni），并且把帧率压低（Qwen3.5-Omni 的输入只有 6.25 Hz）。
  2. 滑动窗口并不安全。 2026 年 10 月的 Why Full-Duplex Speech Models Collapse in Long Conversations 发现，Moshi 和 PersonaPlex 在窗口滑走第一个 KV 条目之后，会退化成沉默和乱码（§4.1）；重复则来自另一个机制，即“自我强化重复”。把这个条目钉住（IAP，§5），再加上重复惩罚（DRP），不需要重训，在长达 1 小时的回放中就能显著减少崩溃（§6.2）。但问题没有根除：PersonaPlex 仍有不少沉默段，只是大多能在 1 分钟内恢复。
  3. 工具调用已经收敛到“快慢双系统 + 异步委托”这一种做法。 SALMONN-duo、OpenAI GPT-Live、DuplexOmni、KAME、MoshiRAG，以及 2609.19334 的前后端方案，做法都一样：前端负责实时听说，并说一些填充语（“我帮你查一下”）；后端是文本 LLM 或 agent，负责推理和调工具；结果以精简文本的形式回注前端。直接把工具返回塞进音频时间线的方案只有 NemotronLabs VoiceChat，它的代价是每个会话建议挂载的工具不超过 5 个，多工具同时调用还不可靠，训练音频窗口也只有约 2 分钟（§7）。
  4. 商用系统靠“压缩 + 重启”撑住长会话。 Gemini Live 用 80% 触发的滑动窗口；GPT-Live 在上下文用到 90% 时启动一个“替换引擎”，只带 8,192 token 的历史摘要过去；阿里云 Realtime 硬性限制只保留 100 轮、600 秒音频。这三种做法都说明，原始音频不适合做长期记忆，跟上次讨论里“分层记忆”的判断一致。

怎么读这张表

  • Moshi 的 12.5 位置/秒，在原生双工模型里其实算省的：它把双方的音频和文本相加进同一个位置，而不是排成一串。FLM-Audio 的引言专门指出，SALMONN-omni 这类时分复用的序列长度会随通道数线性增长。
  • SALMONN-omni v2 的推算过程：编码器 25 Hz（§4.1），80 ms 一块，所以每块有 2 个环境 embedding，加上 2 个助手 embedding，再加 1 个文本 token，共约 5 个位置，折合 62.5/秒。这还没算可能存在的块边界 token。SALMONN-duo 明确写了去掉 echo 流是“to reduce sequence length and support longer conversational tasks”（§3.1.1），说明作者自己也认为这是瓶颈。
  • 真正便宜的是 Freeze-Omni、MinMo、MiniCPM-o 4.5、Qwen-Omni 这几家。它们不把生成的语音放回 LLM，LLM 的历史只有“输入音频特征 + 文本”。代价是模型听不到自己说了什么，所以回声消除和自我打断检测更难做：SALMONN-omni v2 的实验显示，Freeze-Omni 在有自身回声时性能大幅下降（§5）。

三、分家族细看¶

3.1 Moshi 系：多流并行，滑动窗口¶

  • 结构：Helium 7B 作为 Temporal Transformer，每 80 ms 一步，加一个小的 Depth Transformer 逐层预测 8 个 codebook（§3.4）。Mimi 是 12.5 Hz、8 个 codebook、1.1 kbps，第一层蒸馏自 WavLM 的语义（§3.3.1）。文本通道是 Inner Monologue：带 padding、与语音按时间对齐的文本（§3.4.4）。
  • 上下文：3000 步，约 4 分钟，推理时用滑动窗口。
  • 衍生工作：
  • Hibiki 直接只用 500 步（40 秒）局部注意力。这说明对同传这类“只需要短期记忆”的任务，短窗口就够了。
  • PersonaPlex（NVIDIA，2026-01）加了“混合系统提示”：文本角色写进 agent 文本通道，音色样本放进 agent 音频通道。上下文机制没改。
  • Unmute / DSM 是 Kyutai 自己做的级联方案（流式 STT → 任意文本 LLM → 流式 TTS）。从侧面看，这说明 Kyutai 在需要长上下文和工具的产品里，也没有坚持用原生 Moshi。
  • 工具方向的尝试（见第五节）：MoshiRAG、KAME、Context Spanning。

3.2 SALMONN-omni 系：不用 codec 的单 LLM 双工¶

v1（2411.18138，2024-11）是一篇短技术报告。它提出用“时间块 + <think> 占位 token”让 LLM 在听的时候也有东西可输出，避免用普通占位符导致输出分布塌缩。块大小、骨干模型等细节都没给。

v2（2505.17060，NeurIPS 2025）：

  • 两条输入流（§3，Figure 1）：环境流包括用户语音、背景声和自身回声；助手流是自己此前输出的语音，经编码器得到的 embedding，论文称之为 dual-channel input。两条流和文本 token 交错成一条自回归序列。
  • 规格（§4.1）：Mamba 流式编码器（从 Whisper-large-v3 蒸馏，25 Hz），Llama-3-8B-Instruct + LoRA，80 ms 一块、每块 1 个文本 token。LLM 每出 4 个 token，CosyVoice2-0.5B 合成器就生成 12 个语音 token（480 ms），所以首包延迟 320 ms。
  • “思考”token（§3.3，Figure 2）：显式的 <think> / <shift> 写进序列，效果优于隐式预测 listen/speak。这里的“思考”指的是话轮状态控制，不是推理。
  • 关键发现（§5.1）：加入助手流之后，AlpacaEval 上的话轮转换成功率从约 70%（Stage 1）升到约 90%（Stage 2）。也就是说，“听到自己”对双工行为很重要，但它也直接翻倍了序列长度。上下文与双工质量之间的张力，在这里体现得最清楚。
  • RL：第三阶段用 DPO 修正 SFT 模型“太容易被打断”的偏差（§5.3.2，附录 D）。
  • 上下文管理：论文没有提到截断、滑窗或 KV 管理。

SALMONN-duo（2609.34247，2026-09），也就是 SALMONN-omni 的工具化版本：

  • System 1 是 SALMONN-omni 前端，去掉了 echo 流来缩短序列（§3.1.1）。System 2 是可以即插即用的异步后端：LLM、工具编排器，真实部署中甚至用过 Codex（§3.1.2，附录 F）。
  • 前端只决定要不要委托：发出 DELEGATE token，或由隐藏状态上的委托头决定（§3.1.3）。意图理解和执行都交给后端。后端的对话历史由流式 ASR 构建，是纯文本。
  • 训练分两步：先用“知识边界感知 SFT”，通过 N 次 rollout 判断模型自己能不能答对来打标签（§3.2）；再做 cost-aware GRPO，奖励排序为“直接答对 > 委托后答对 > 答错”（§3.3）。
  • 后端结果按每个时间块插入 N=100 个 token 的方式回注前端（§3.1.1）。这意味着结果回来的那一刻，前端序列会出现一次跳增，但工具的原始返回不会进入前端。

3.3 模块化双工：Freeze-Omni、MinMo、VITA¶

  • Freeze-Omni：Qwen2-7B 全程冻结，只训练编码器、适配器、prompt embedding 和语音解码器。输入是 12.5 Hz 的 chunk。最后一层的分类头预测三种状态：继续听 / 打断并回答 / 不打断（§2.4）。语音 token（TiCodec，40 Hz）从不回到 LLM，LLM 历史就是文本和输入特征。部署时把每个用户的 KV cache 单独存放，以“模型即服务”的方式调度。上下文成本最低，但实际延迟约 1.2 秒（§3.5），而且对自身回声敏感。
  • MinMo：约 8B（Qwen2.5-7B）。外挂的 Full Duplex Predictor 决定是否回应、是否停止播放，语音由独立的 voice token LM 生成，同样不回灌 LLM。全双工延迟理论上约 600 ms，实际约 800 ms。
  • VITA-1.0：两个模型实例轮流做“生成”和“监听”，发生有效打断时互换角色。VITA-1.5 的论文里没检索到双工机制的描述 [存疑]。

3.4 时分交错单序列：SyncLLM、OmniFlatten、BayLing-Duplex、MiniCPM-o 4.5¶

  • SyncLLM（Meta）：HuBERT 25 Hz 单元，去掉重复后语义密度提高约 50%，用同步 token 保持时间。为了抵消网络延迟，它先预测用户的下一个 chunk，真实输入到了再替换。上下文就是 Llama3-8B 的 8,192，论文在局限性一节明确承认上下文长度是瓶颈（§7）。
  • OmniFlatten：Qwen2-0.5B，训练时从 4 流逐步减到 3 流再到 2 流，用 chunk 展平。
  • BayLing-Duplex（2026-06）：基于 GLM-4-Voice，文本通道里用 4 个状态 token（[SILENCE]、[ASSISTANT]、[PAD]、[EPAD]）来决定听、说、停。上下文不滑窗，持续增长，约 17.5 分钟后填满。2610.32349 观察到它在填满之前就已经开始出现乱码和沉默（Figure 2）。
  • MiniCPM-o 4.5（2026-04）：自称“第一个全双工全模态 LLM”。每个 1 秒窗口内是“视觉 / 音频 / 输出”三段，静默时输出 [listen]，不依赖外部 VAD。消融实验中 1.0 秒的窗口优于 0.2 秒和 0.1 秒（§3.3）。LLM 只输出文本，另由一个 0.3B 的语音解码器负责发声，所以历史开销很小。

3.5 Thinker-Talker：Qwen-Omni 系列¶

  • Qwen2.5-Omni：25 Hz 输入，TMRoPE，32k 上下文，轮次式。
  • Qwen3-Omni：AuT 编码器 12.5 Hz，Thinker 是 30B-A3B MoE，Talker 是 3B-A0.3B MoE，首包 234 ms（§2.5）。关键设计是 Talker 不再读取 Thinker 的文本表示，明确为外部模块（RAG、函数调用、安全过滤）在“说出来之前”介入 Thinker 文本留出了口子（§2.1）。
  • Qwen3.5-Omni（2026-04）是这次对比里在上下文上最激进的一家：
  • 输入压到 6.25 Hz（16 倍下采样，§2.2）；
  • 骨干换成 Gated DeltaNet 混合注意力 MoE，用来降低长序列的 KV I/O（§2.5）；
  • 上下文 256k，可容纳 10 小时以上的音频（§1）；
  • 原生支持 WebSearch / FunctionCall，并号称支持语义打断。
  • 这基本对应上次讨论里的三条路线：降低帧率、线性注意力或 SSM 混合、文本域承载工具。不过它本质上仍是“轮次式 + 打断识别”，不是 Moshi 那种逐帧并行。

3.6 轮次式基线：GLM-4-Voice、Step-Audio 2、Kimi-Audio¶

这几家不是全双工模型，放在这里作参照。

  • GLM-4-Voice 按 13 文本 : 26 语音交错，生成的语音 token 会进入历史。
  • Step-Audio 2 是开源模型里少数原生支持工具的：网页搜索、天气、时间，以及“音频检索”（从声音库里检索音色）。检索结果直接拼在输入音频特征之后。它的上下文是 16k，而且历史会预填交错序列，长对话成本高。
  • Kimi-Audio：12.5 Hz 离散语义 token 加上连续 Whisper 特征，没有工具调用。

四、上下文管理策略谱系¶

下表把各家的做法按作用层级归类，大致从“推理时临时补救”到“架构层面根治”排列。

推理时 KV 锚点钉住（IAP）+ 重复惩罚（DRP） 2610.32349 §5，结果见 §6.2 不需要重训，在 1 小时回放中显著减少崩溃，但没有根除；只解决“少崩”，不解决“记得住”

表示层 去掉部分输入流 SALMONN-duo 去掉 echo 流 可能削弱话轮判断（v2 显示助手流能把成功率从 70% 提到 90%）
表示层 降低帧率 Qwen3.5-Omni 6.25 Hz；Qwen Realtime 计费 7 tok/s 细粒度韵律和打断时机可能受损
表示层 外部信息用加法注入，而不是插入 MoshiRAG（附录 A.2.1） 作者承认插入的效果更好，但为了序列长度选择了相加
架构层 混合线性注意力 Qwen3.5-Omni（Gated DeltaNet）、NemotronLabs（Mamba-Transformer） 精确回忆能力弱
系统层 摘要压缩 + 滑窗 Gemini Live（80% 触发）、GPT-Live 后台摘要 摘要会丢失副语言信息
系统层 替换引擎 GPT-Live：用到 90% 时新起一个引擎，带 ≤8k 历史 新引擎只看得到摘要和最近消息
系统层 轮数 / 时长硬上限 Qwen-Omni-Realtime（100 轮 / 600 秒音频） 简单粗暴
系统层 快慢双系统：后端持有文本长历史 SALMONN-duo、GPT-Live、DuplexOmni 需要解决异步、乱序结果的融合

值得注意的一点：2610.32349 提出了一个假设：锚点被淘汰后之所以崩溃，是因为“训练时缓存为空，推理时却持续运行”的分布不匹配。这呼应了上次讨论提到的“训练端也受影响”。另外，它在 附录 B.1 中指出，钉住的锚点起到了 attention sink 的作用，这跟 StreamingLLM 的思路一致；它还报告自己的方法比 StreamingLLM 式的基线更快（§6.4）。

Gemini 的三种 scheduling 很有参考价值。它把“工具结果回来之后要不要打断当前说话”变成了一个显式的决策维度，而大多数学术方案（SALMONN-duo、MoshiRAG）把这件事交给模型隐式处理。如果你要做评测，这可以单独拿出来作为一个评估维度。

六、与对话交互研究的关系¶

把这次对比和上次讨论的“三层记忆”对照来看：

  • 工作记忆（原始音频，短窗口）：已经有很多实证支持。Hibiki 用 40 秒就够；Moshi 加上 IAP+DRP 后，在 1 小时的回放中崩溃明显减少；MiniCPM-o 和 Freeze-Omni 干脆不在 LLM 里保存自己的语音。
  • 情景记忆（压缩表示）：这是目前最大的空白。 商用系统用的是文本摘要（GPT-Live、Gemini），学术界基本只做了“滑窗丢弃”，或者“相加注入”这类无压缩的方式。目前还没有看到“按话轮把音频压成少量 latent，同时保留副语言信息”的工作。这可能是一个值得切入的研究点。
  • 语义与工具记忆（文本后端）：已经收敛到双系统。剩下的难点是：
  • 什么时候委托（SALMONN-duo 用知识边界 + GRPO 来学）；
  • 结果回来后怎么插话（Gemini 的三种 scheduling，SALMONN-duo 的乱序处理）；
  • 前端和后端的历史怎么保持一致（SALMONN-duo 的后端只能看到 ASR 转写，看不到语气）。

几个可以做的实验方向（供参考）：

  1. 在 SALMONN-omni 或 Moshi 上做“话轮级压缩记忆”：窗口外的音频压成 K 个 gist token，并保留情绪 / 说话人标签。跟纯滑窗和 IAP 对比，在 FD-LHB 这类长时程基准上评测。
  2. 测量“助手流”的边际价值：SALMONN-omni v2 说它把话轮成功率从 70% 提到 90%，SALMONN-duo 又把它去掉了。在长对话设置下，这个取舍值得重新做一遍消融。
  3. 把工具结果回注时的 scheduling 策略作为一个独立的评估轴：打断、等空闲还是静默吸收，比较用户体验和任务成功率。

七、存疑与不一致之处¶

  • SALMONN-omni 的“echo 流”定义不一致：v2 论文说的是两条流，环境流里包含 echo，助手流是自己之前输出的语音（§3）。SALMONN-duo 回顾时却写成“user, echo and assistant 三条流”（§3.1.1）。因此“去掉 echo 流”具体去掉了什么不确定，表中的 37.5 位置/秒只是推算。
  • SALMONN-omni v1 的 <think> 损失权重：从 HTML 摘录看似乎是负权重，但没能确认。
  • OmniFlatten、LSLM、MinMo 都没有给出进入 LLM 的帧率，所以表中没有填。
  • Moshi 的有效上下文：Helium 预训练用的是 4096 token，Moshi 用 3000 步。两者不是同一个单位，不要混为一谈。
  • Qwen3.5-Omni 的工具能力：在 BFCL-V4 / TAU2Bench 表格里，没能核对哪一列对应哪个模型。
  • gpt-realtime 的“异步函数调用”：发布博客里提到了，但没读到具体原文；新版 GPT-Live 改成了委托机制。
  • 2026 年的多篇论文（BayLing-Duplex、FLAIR、LWS、2605.10199 等）只读了摘要。其中 2605.10199（“LLM 应该如何边说边听”）的结论很相关：把用户流直接放进输入，QA 效果更好，但被打断时上下文更容易被污染；用交叉注意力做外部记忆，则能更好地保住生成上下文。建议精读。
